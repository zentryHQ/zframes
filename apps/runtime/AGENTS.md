# apps/runtime

The Vite app that IS the runtime, and the app `pnpm build:cli` vendors into the
CLI's prebuilt bundle.

## How it renders

the Vite app that IS the runtime. `App.tsx` **fetches** its spec at runtime from `/__zframes/dashboard.json` (served by the dev plugin under `pnpm dev`, by `zframes serve` in prod) and renders it through `DashboardEditor` (not the bare `DashboardRenderer`), so it's end-user-editable; `onSave` PUTs the edited spec to `/__zframes/dashboard` and reloads. **It imports no data provider.** In parallel with the spec fetch it GETs `/__zframes/providers` and loads exactly the plugins the server names, each as its own lazy chunk (`resolveRuntimeProviders`, `@zframes/plugins/load` — memoized so StrictMode's double-effect never constructs a second fleet/socket); route absent or failing → the synthetic demo, so a static host still renders. The board renders only once BOTH spec and providers are in, and an all-synthetic mount badges the header "demo data" (a market dashboard must never pass generated numbers off as live). Dev's mounted set is the host composition in `vite.config.ts` (fleet + keyed tier); prod's is the operator's `zframes providers` set. Tailwind v4 via `@tailwindcss/vite` (`@source` scans workspace packages). `pnpm build:cli` `vite build`s this app into the CLI's `runtime/`. Renders `spec.background` via `src/background.tsx` (Unicorn Studio scene through the shared `@zframes/unicorn` loader, lazy-loaded, behind a contrast scrim). Renders a pinned live ticker tape via `src/ticker-tape.tsx` (`TickerTape`) — **host chrome, not a frame**: always-on, fixed to the viewport bottom, outside the editable grid, never declared in the spec. The header carries a `src/dashboard-chooser.tsx` (`DashboardChooser`) — also host chrome: it GETs `/__zframes/dashboards`, and when `serve` reports `canSwitch` with >1 store dashboard it turns the title into a button opening a card-overlay chooser; picking a card POSTs `/__zframes/switch` then reloads. Otherwise (dev, explicit-path serve, single dashboard) it falls back to the static title. `serve` always opens the default dashboard — the chooser is on-demand, never a forced landing. It runs inside `<FramesProvider>` (shares the app's providers, no extra WS), surfaces stocks first (`getDayStats(["xyz:*"])`) then the crypto universe (`getDayStats()`), each with a logo + live mid + 24h change, in a CSS marquee.

## Dashboard background

- Dashboard background: the **spec declares** it (`background: {type: "gradient"|"unicorn"|"none", projectId?, opacity?}`), the **host renders** it (runtime's `background.tsx`) — same split as providers. Scene `opacity` is kept moderate (~0.15) so it reads as a living backdrop in the gutters, not a distraction; cards are opaque so content always wins. The Unicorn Studio engine lives only in the hosts, never in core — loaded by the shared in-house loader (`@zframes/unicorn`, used by both the runtime background and the explorer front door), NOT the `unicornstudio-react` npm package (which inlines a ~1.3 MB copy of the engine into the bundle even when you load it from a URL, as we do). **Footgun:** a `unicorn` background injects the self-hosted engine (`apps/runtime/public/unicornStudio.umd.mjs`, shipped in the prebuilt bundle — not a CDN) and fetches the scene from a hosted Unicorn Studio project (Aurora, `SCENE_DEFAULT_PROJECT_ID` in `@zframes/spec`, is the zframes default) — keyless, but the scene fetch is still an external runtime dependency; it falls back to the body gradient if the engine or scene fails to load. The skill emits `unicorn` by default.
